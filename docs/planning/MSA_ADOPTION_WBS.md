# 차세대 MSA 프로젝트 도입 WBS

- 기준일: 2026-10-20 (Asia/Seoul)
- 기준: 현재 작업 공간의 구현·기존 실행 증적 + [관측·운영 기반 설계](../architecture/OBSERVABILITY_FOUNDATION.md) + [개발 로드맵](../MSA_DEVELOPMENT_ROADMAP.md).
- 현재 판정: **개발 기반과 일부 샘플 재사용 가능. 차세대 운영 프로젝트에 즉시 적용 가능한 상태로 판정하지 않음.**
- 범위: 처리 flow 추적, 오류 추적, 서비스 장애 판정의 최소 운영 기반을 실제 업무 한 건으로 검증한다. Redis·Kafka는 후속 범위이며 본 WBS 공수에서 제외한다.
- 본 문서는 계획이다. 작업 완료·담당자 배정·일정 확정 또는 운영 인수를 의미하지 않는다.

## 1. 현행 구현과 재사용 판정

| Auth·Gateway 인증 | BCrypt·RS256·권한·내부 인증·DB Refresh/감사 및 공격 거부 검증 | 샘플 보안 기반 재사용 | 운영 Secret/TLS·기존 데이터 migration·보안 인수 |

| 오류·서비스 장애 운영 기능 | 일부 오류 필드/health 존재, 그룹화·상태 판정·알림 없음 | 설계 기준부터 구현 필요 | WBS 5~7 |
| 기반 설계·로드맵 | 문서 작성 완료 | 설계 입력으로 사용 | 프로젝트 요구 확정 및 구현/시험 필요 |

증거 위치: 루트 build.gradle/settings.gradle/gradle-wrapper.properties, hr-service/src/test 및 build/test-results/test, 서비스별 controller/service/schema. 이전 실행 로그는 현재 환경의 `/workspace/cloud-setup/JAVA25_VALIDATION.md`, `wrapper25-build.log`, `java25-smoke.log`에 있다. 환경 밖으로 인계할 때 해당 증적을 승인된 저장소에 이관해야 한다. 최초 WBS 작성에서는 기존 증적과 소스를 교차 확인했으며, 이후 1~2단계 수행에서 새 시험을 실행했다. 최신 결과는 단계별 증적을 따른다.

현재 변경에는 미커밋 파일이 포함된다. 원격 main에 반영·릴리스됐다는 의미가 아니며 도입 baseline은 검증 후 별도 태그/이미지로 고정한다. 기존 구현은 잔여 공수에 다시 계산하지 않는다.

## 2. “즉시 도입 가능”의 판정 기준

| Gate | 통과 조건 | 현재 |
|---|---|---|
| G0 요구 확정 | 환경·업무·성능/가용성·보안·보존·복구 목표와 책임자 확정 (1번 작업군) | 진행중 — 회원가입 샘플·단일 VM 우선 검증 확인, 운영 목표·인수자 미확정 |
| G1 안전한 업무 진입 | 기존 오류 복구 + 인증/인가/서비스 접근 경계 (2~3번) | 2~3번 샘플 로컬 검증 완료; 운영 키·망/TLS 등 보안 인수는 후속 |
| G2 처리 flow·오류 추적 | 동일 업무의 단계/호출/원인 오류 연결, 중요 이력 복구, 중복/순서 제어 (4~5번) | 미충족 |
| G3 장애 탐지·운영 조회 | 서비스/인스턴스·UNKNOWN 구분, 실제 지표·화면·알림 (6~7번) | 미충족 |
| G4 배포·복구 재현 | CI/설정/Secret/이미지/영속 DB/롤백/복원 (8번) | 미충족 |
| G5 실제 업무 인수 | G0~G4 및 통합·장애·부하·보안 시험, 차세대 업무 1건 실연/인수 (9번) | 미충족 |

G0~G5를 모두 통과한 검증 버전만 합의한 환경·업무·부하 범위에서 도입 가능으로 판정한다. 다른 업무·용량·다중 인스턴스에는 추가 검증이 필요하다. 제안서의 probe 주기/보존 기간/오버헤드 수치는 운영 목표로 확정된 값이 아니다.

## 3. WBS 상세

상태는 현행 코드의 존재 여부와 구분한다. 아래 항목은 잔여 보완/신규 작업이다. **1.1은 우선 검증 범위 사용자 확인·시험용 제안값 진행, 운영 요구 확정 대기, 1.2는 개발 계약 초안 검증 완료·확정 대기, 1.3은 로컬 격리 검증 완료·운영 환경 대기**이며 **2.1~2.3은 샘플 개발 검증 완료**, **3.1~3.4는 샘플 보안 검증 완료**, 4번 이후는 미착수다. 상세 증적은 [1단계 결과](stage1/RESULTS.md)와 [2단계 결과](stage2/RESULTS.md), [3단계 결과](stage3/RESULTS.md)를 따른다. BE=백엔드, FE=화면, OPS=인프라/운영, QA=검증, 설계/업무=설계 책임자와 업무 인수자. 역할은 제안이며 실명·가용 인력은 1.1에서 확정한다. 각 작업 공수에는 자체 구현·테스트·문서를 포함하고, 9번은 별도의 통합 인수/비기능 시험 공수다. 선행 ID는 해당 작업이 완료된 뒤 착수한다는 뜻이다.

## 4. 공수와 실행 순서

| 작업군 | 잔여 공수(PD) |
|---|---|
| 1. 요구·계약·검증 기반 | 6~10 (최초 계획, 일부 수행·잔여 미재산정) |
| 2. 기존 통합 흐름 복구 | 4~7 (최초 계획, 개발 검증 완료·실제 공수 미입력) |
| 3. 인증·보안 기반 | 10~17 (최초 계획, 샘플 보안 검증 완료·실제 공수 미입력) |
| 4. 처리 flow·수집 신뢰성 | 21~34 |
| 5. 오류 추적·감사 | 9~14 |
| 6. 서비스 장애 판정·알림 | 13~20 |
| 7. 통합 운영 화면 | 9~15 |
| 8. 배포·운영 재현성 | 9~15 |
| 9. 도입 적합성 검증·인수 | 14~22 |
| **합계 (33개 작업)** | **95~154 PD (최초 계획)** |

위 공수와 상세 표의 잔여 PD는 착수 전 최초 추정값이다. 1~3단계 진행 후 실투입·미확정 범위가 있어 현재 잔여 공수로 다시 합산하지 않는다. 실제 공수는 입력되지 않았으며 임의 완료율/감산을 적용하지 않았다. PD는 1인 1일 작업량이며 달력 기간과 같지 않다. 현재 샘플의 제한된 범위에 대한 초기 추정으로, 요구/운영 환경 확정 후 재산정한다. 기존 완료 작업, 조직 조달·보안 승인 대기, 외부 연계 개발, 기존 대량 데이터 정비, Redis/Kafka 도입은 포함하지 않았다. 인수 시험에 대한 통상 수정은 포함하지만 신규 요구·대규모 재설계는 별도 산정한다.

실행 순서는 다음과 같다.

1. **준비:** 1.1 → 1.2/1.3. 도입 기준과 데이터/오류 계약부터 고정한다.
2. **복구·보안:** 2번과 3번을 각각 선행 조건에 따라 진행한다. 안전한 진입과 회귀 기준을 확보한다.
3. **핵심 구현:** 4번 flow·내구 수집과 5번 오류 기능을 연결한다. 6번 probe·메트릭 및 8번 배포 준비는 명시된 선행 작업 완료 후 병행할 수 있다.
4. **운영 완성:** 대응 API가 준비된 화면부터 7번을 구현하고 6.4 알림과 8.3 복구를 연결한다.
5. **도입 검증:** 9.1 → 9.2 → 9.3 → 9.4 순으로 통과하고 검증 버전을 고정한다.

인력과 가용률이 정해지지 않아 착수일·종료일·확정 납기는 두지 않는다. 달력 일정은 작업별 역할 배정과 선행 관계를 반영해 별도로 산출한다. 총 PD를 단순히 인원수로 나눈 값을 확정 납기로 사용하지 않는다.

## 5. 인수 증적과 진행 관리

- 작업마다 담당자, 실제 시작/완료일, PR/커밋, 시험 결과, 잔여 결함, 인수자를 기록한다. 계획 공수와 실제 공수를 구분한다.
- 완료 판정은 산출물 존재와 완료 기준 시험을 모두 요구한다. 코드만 작성했거나 build만 통과하면 기능 완료로 처리하지 않는다.
- 보안상 중대 결함, 가입/추적 경로 차단, 중요 업무 이력 유실, 장애·미관측 오판정, 합의 복구 목표 미달은 도입 차단 항목으로 관리한다.
- 부하/보존 비용·오탐/탐지 시간·계측 오버헤드·복원 결과는 실제 수치와 시험 환경을 함께 보관한다.
- 9.4 인수 시 소스/이미지 버전, DB migration, 설정 목록, API·이벤트 계약, 시험 성적, 운영/장애 대응 문서, 담당자/연락 체계와 교육 기록을 묶어 인계한다.
