# MSA 플랫폼 개발 순서

현재 서비스와 Trace 기능을 기반으로 신뢰성, 보안, 운영 기능을 순서대로 보강한다. Redis와 Kafka는 후속 단계에서 도입한다. 이 문서는 개발 계획이며, 아래 항목이 구현 완료되었다는 의미는 아니다.

차세대 프로젝트의 핵심 요구인 **처리 flow 추적·오류 추적·서비스 장애 여부**는 [관측·운영 기반 설계](architecture/OBSERVABILITY_FOUNDATION.md)를 기준으로 개발한다. 해당 설계의 A~F 순서는 이 로드맵의 오류 복구·인증·API 계약·호출 안정성·관측성·운영 기능을 연결한 우선 구현 경로다.

현행 구현과 잔여 개발 작업을 구분한 실행 계획은 [차세대 도입 WBS](planning/MSA_ADOPTION_WBS.md)를 따른다. 작업별 선행 조건, 담당 역할, 산출물, 완료 기준, 초기 공수를 포함한다.

## 개발 원칙

- Java 25와 현재 적용한 Spring Boot / Spring Cloud 호환 버전을 기준으로 개발한다.
- 기존 서비스 경계를 유지하고 서비스별 H2로 기본 흐름을 검증한다.
- 내부 동기 호출은 Feign, 외부 호출은 RestClient 또는 WebClient를 사용한다.
- 모든 단계에서 Gateway 경유 성공·실패 요청과 동일한 `X-Trace-Id` 전파를 확인한다.
- 각 단계의 완료 기준을 충족한 뒤 다음 단계로 진행한다. 테스트와 필요한 문서는 해당 기능과 함께 추가한다.
- Redis/Kafka 없이 진행하는 초기 단계는 단일 인스턴스를 기준으로 한다. 인메모리 상태를 다중 인스턴스 공용 상태로 간주하지 않는다.

## 전체 순서

| 단계 | 개발 항목 | 주요 대상 | 선행 조건 |
|---|---|---|---|
| 1 | 기존 오류 수정 및 통합 흐름 복구 | Gateway, Member, HR, 테스트 UI, Trace | 현재 빌드 환경 |
| 2 | 인증·인가 강화 | Auth, Gateway | 1단계 |
| 3 | API 계약과 오류 처리 표준화 | 업무 서비스, 테스트 UI | 1~2단계 |
| 4 | 서비스 호출 장애 대응 | Gateway, Member, 내부·외부 클라이언트 | 3단계 |
| 5 | 중복 요청 방지와 프로세스 상태 정합성 | Member 및 저장 API | 3~4단계 |
| 6 | Trace 조회·분석과 감사 이력 | Trace, 업무 서비스, 테스트 UI | 1~5단계 |
| 7 | 상태 점검·메트릭·알림 | 전체 서비스 | 4~6단계 |
| 8 | 설정·비밀 관리와 배포 자동화 | Config, 전체 서비스, CI/CD | 1단계부터 병행, 운영 배포 전 완료 |
| 9 | Redis 도입 | 캐시·분산 상태가 필요한 서비스 | 1~8단계 및 다중 인스턴스 요구 |
| 10 | Kafka 도입 | 비동기 후속 처리가 필요한 서비스 | 1~8단계 및 이벤트 처리 요구 |

9~10단계는 후속 계획이다. Kafka 자체가 Redis에 의존하는 것은 아니며 실제 요구에 따라 각각 도입한다.

## 1. 기존 오류 수정 및 통합 흐름 복구

개발 항목:

- Gateway Trace 필터의 `block()`을 제거하고 리액티브 체인으로 요청과 Trace 기록을 연결한다.
- Member가 HR 응답의 실제 필드인 `active`를 사용하도록 계약을 맞춘다.
- 테스트 UI의 중계 컨트롤러에서 인증 헤더와 Trace ID를 Gateway로 전달한다.
- Gateway에 Trace 조회 라우팅을 추가하고 조회 권한을 구분한다.
- 가입 프로세스에서 요청의 Trace ID를 재사용하고 Feign 호출에도 전달한다.
- 문서의 서비스 포트와 실제 설정을 일치시킨다.

완료 기준:

- Gateway → Member → HR 회원가입이 ACTIVE 직원에 대해 성공한다.
- INACTIVE·미등록 직원은 정의한 업무 오류로 거부된다.
- UI에서 로그인 후 보호 API와 Trace 조회를 사용할 수 있다.
- 하나의 요청이 Gateway·업무 서비스·하위 호출에서 같은 Trace ID로 조회된다.
- 기존 오류를 재현하는 회귀 테스트와 전체 빌드가 통과한다.

## 2. 인증·인가 강화

개발 항목:

- 비밀번호를 검증된 단방향 해시로 저장하고 모든 조회 응답·로그에서 제외한다.
- 형식 기반 샘플 토큰을 서명·만료·발급자·대상 검증이 가능한 JWT로 교체한다.
- 일반 사용자와 관리자 등 필요한 역할의 RBAC를 적용한다.
- Refresh Token의 저장·만료·회전·폐기 정책을 정의한다. 초기에는 Auth 서비스 DB를 사용한다.
- 외부 요청은 Gateway를 경유하도록 하고, 직접 서비스 접근과 내부 호출의 인증 정책을 명시한다.

완료 기준:

- 위조·만료·잘못된 발급자의 토큰은 401, 권한 부족은 403으로 처리된다.
- 로그아웃·토큰 재발급 후 폐기한 Refresh Token을 재사용할 수 없다.
- 비밀번호 원문과 해시가 API 응답·Trace·로그에 노출되지 않는다.

## 3. API 계약과 오류 처리 표준화

개발 항목:

- 공통 오류 코드와 HTTP 상태, 입력 검증, 페이지네이션, 날짜 형식을 정의한다.
- OpenAPI 문서와 서비스 간 계약 테스트를 추가한다.
- HR의 독립 응답 계약은 유지하고 Member에서 필요한 값을 해석한다.
- 인증 실패·입력 오류·업무 거부·하위 서비스 장애를 서로 다른 코드로 구분한다.

완료 기준:

- API 문서와 실제 응답이 일치하고 필수 필드 누락·잘못된 입력이 검증된다.
- HR 응답의 `active` 같은 필드 변경을 계약 테스트가 감지한다.
- 테스트 UI가 성공·업무 실패·통신 실패를 구분해 표시한다.

## 4. 서비스 호출 장애 대응

개발 항목:

- Feign·RestClient·WebClient의 연결·응답 Timeout을 명시한다.
- Circuit Breaker를 적용하고 필요한 경우 동시 호출 수를 제한한다.
- 일시적 장애에만 제한 횟수·백오프를 둔 Retry를 적용한다. 저장 요청은 5단계 중복 방지가 마련되기 전 자동 재시도를 피한다.
- Trace 저장 장애가 업무 요청에 미치는 영향과 Trace 유실의 관측 방법을 정의한다.
- fallback은 실제 성공과 구분하고 인증·자격 검사를 임의 성공 처리하지 않는다.

완료 기준:

- HR 지연·연결 실패 시 요청이 정해진 시간 안에 종료된다.
- 장애 서비스의 반복 호출이 차단되고 복구 후 호출이 재개된다.
- Trace 수집 장애 시 업무 처리 결과와 수집 실패를 각각 확인할 수 있다.

## 5. 중복 요청 방지와 프로세스 상태 정합성

개발 항목:

- 저장 API에 Idempotency Key를 도입하고 서비스 DB에 처리 상태·결과를 기록한다.
- 같은 키로 다른 본문을 보내는 경우, 처리 중 재요청, 보관 기간을 정의한다.
- DB 제약과 트랜잭션으로 동시 중복 요청을 제어한다.
- 프로세스·단계의 상태 전이를 정의하고 HTTP·DB 오류를 포함한 실패 경로에서 종료 상태를 기록한다.
- HR 자격 거부와 외부 응답 시간 초과를 다른 상태·오류 코드로 기록한다.

완료 기준:

- 같은 요청을 재전송하거나 동시에 보내도 업무 데이터가 중복 생성되지 않는다.
- 완료된 요청의 결과를 재조회할 수 있고 다른 본문으로 키를 재사용하면 거부된다.
- 하위 서비스 장애·DB 실패 뒤 프로세스가 영구히 RUNNING으로 남지 않는다.

## 6. Trace 조회·분석과 감사 이력

개발 항목:

- 기존 Trace 기능에 Trace ID·Process ID·서비스·상태·기간별 검색과 페이지네이션을 보강한다.
- 호출 타임라인, 서비스별 소요 시간, 실패 단계와 오류 코드를 표시한다.
- 필요하면 OpenTelemetry 표준의 trace/span 문맥과 기존 `X-Trace-Id`의 연결 방식을 정한다.
- 요청·응답 수집 범위, 민감정보 마스킹, 보관 기간, 삭제 정책을 적용한다.
- 업무 데이터 변경의 주체·시각·대상·변경 내용을 감사 이력으로 남긴다. 실행 경로를 설명하는 Trace와 감사 이력을 구분한다.

완료 기준:

- 가입 한 건의 전체 호출 흐름과 실패 지점을 화면에서 확인할 수 있다.
- 인증 오류·업무 오류·시스템 오류를 구분하고 Trace 조회 권한을 검증한다.
- 민감정보 마스킹과 보관 기간에 따른 정리가 검증된다.
- 업무 변경과 감사 이력이 같은 업무 식별자로 연결된다.

## 7. 상태 점검·메트릭·알림

개발 항목:

- Actuator Health·Liveness·Readiness와 정상 종료를 구성한다.
- 요청 수·오류율·응답 시간·DB 커넥션·Circuit Breaker 상태·Trace 수집 실패를 측정한다.
- Prometheus/Grafana 등으로 필요한 운영 지표를 시각화하고 알림 기준을 정한다.
- 사용자 ID·Trace ID처럼 값이 계속 늘어나는 식별자를 메트릭 라벨에 넣지 않는다.

완료 기준:

- 필수 의존성 장애와 종료 중인 인스턴스의 트래픽 수용 상태가 정책대로 바뀐다.
- 오류율·지연 증가를 대시보드에서 확인하고 알림을 실제로 수신한다.
- 알림마다 확인할 로그·Trace·복구 절차가 문서에 연결된다.

## 8. 설정·비밀 관리와 배포 자동화

개발 항목:

- 개발·테스트·운영 설정을 분리하고 Secret은 소스와 설정 조회 응답에서 제외한다.
- 운영 DB 선택과 마이그레이션을 준비한다. H2 샘플과 운영 데이터 보존을 구분한다.
- CI에 전체 빌드·테스트·계약 검증을 연결하고 서비스별 컨테이너 이미지를 생성한다.
- Health 기반 배포, 정상 종료, 롤백, DB 변경의 하위 호환성을 검증한다.
- Kubernetes를 사용한다면 Service/DNS 기반 서비스 발견부터 적용한다. 별도 Registry는 필요한 경우에 도입한다.

완료 기준:

- 신규 환경에서 문서와 자동화만으로 설치·빌드·기동·검증할 수 있다.
- 비밀정보 없이 소스와 이미지를 배포할 수 있다.
- 배포 실패 시 이전 버전으로 복구되고 데이터가 보존된다.

## 9. Redis 도입 — 추후

도입 조건: 조회 부하 또는 여러 인스턴스가 공유할 상태가 실제로 필요할 때 진행한다.

개발 항목:

- 변경 빈도와 조회량을 측정해 캐시할 데이터를 고른다.
- TTL·무효화·캐시 미스·장애 시 DB 조회 정책을 적용한다.
- 다중 인스턴스 Rate Limit과 토큰 폐기 정보 등 필요한 분산 상태를 추가한다.
- DB 기반 중복 방지를 유지하고 Redis 잠금을 데이터 정합성의 유일한 보장으로 사용하지 않는다.

완료 기준:

- 변경한 데이터가 정의한 시간 안에 조회에 반영된다.
- Redis 장애 시 허용한 수준으로 기능이 유지되고 인증·인가 정책이 임의로 완화되지 않는다.
- 여러 인스턴스에서 제한·만료 정책이 일관되게 적용된다.

## 10. Kafka 도입 — 추후

도입 조건: 가입 후 알림·후속 업무처럼 요청과 분리할 처리와 이벤트 소비자가 생길 때 진행한다.

개발 항목:

- 우선 하나의 후속 업무를 골라 이벤트 발행·구독을 적용한다.
- 이벤트 ID·업무 식별자·버전·발생 시각·Trace 문맥을 정의한다.
- Transactional Outbox로 업무 저장과 이벤트 발행 사이의 유실을 방지한다.
- 중복 소비 방지, 순서 보장 범위, 제한적 재시도, DLQ와 재처리 절차를 구성한다.
- 여러 서비스의 데이터 변경을 묶어야 하는 업무에 한해 Saga와 보상 처리를 설계한다.
- Kafka를 감사 이력이나 영구 Trace 조회 저장소의 대체로 간주하지 않는다.

완료 기준:

- 발행·소비 중 프로세스를 중단하고 재시작해도 업무 이벤트가 유실되지 않는다.
- 같은 이벤트를 다시 소비해도 부작용이 중복 발생하지 않는다.
- 실패 이벤트를 조회·재처리할 수 있고 비동기 처리까지 원래 Trace에 연결된다.

## 첫 개발 범위

먼저 **1단계 통합 흐름 복구 → 2단계 인증·인가 → 3단계 API 계약 → 4단계 호출 장애 대응**을 진행한다. 이때 관측 기반 설계 A단계의 식별자·상태·오류 계약을 먼저 고정하고, 이어 한 업무의 flow·오류·서비스 상태를 B~F 순서로 완성한다. 공통 플랫폼 전체를 한 번에 만들기보다 회원가입 흐름을 기준으로 도입 적합성을 검증한다.

Redis와 Kafka 관련 설치·의존성·서비스 추가는 해당 후속 단계에 도달하기 전까지 진행하지 않는다.
